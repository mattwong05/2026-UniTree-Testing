# 通过 SSH 检查和控制上肢

适用范围：本次 `192.168.123.164` 上已有 SDK 的 G1 29 轴设备。机上 Python 3.8 和 `unitree_sdk2py` 已可用，Mac 不需要另外安装机器人 SDK。

## 测试模式必须与控制接口匹配

用户后续确认已吊装并切入调试模式。这与追加复查时运控 RPC 不可用、关节反馈 mode=0 的现象相符，不能把该现象当成电机损坏。需要区分以下路线：

| 测试目的 | 模式/接口 | 当前工具是否适用 |
| --- | --- | --- |
| 只读角度、温度和错误码 | 能收到 `rt/lowstate` 即可；本次调试模式下实测可读 | `read_lowstate.py` 可用 |
| 保留厂家下身运控，只给上身目标 | 运动/运控模式，`rt/arm_sdk` | `upper_body_check.py` 属于此路线，主动控制仍未验证通过 |
| 吊装下的底层逐轴驱动检查 | 调试模式，专用 `rt/lowcmd` 程序，并确认厂家运控已释放控制权 | 本项目尚未提供该执行程序 |
| 图中的诊断姿势循环 | 厂家内置诊断分支 | 属于预设动作，不等于任意单关节控制 |

官方 [Motion 文档](https://github.com/unitreerobotics/xr_teleoperate/wiki/Motion)明确将 `arm_sdk` 放在运控模式使用；官方 [G1 底层示例](https://github.com/unitreerobotics/unitree_sdk2_python/blob/master/example/g1/low_level/g1_low_level_example.py)使用 `rt/lowcmd` 并先释放运控。两条接口的控制权、命令字段和停止行为不能混用。当前 `--hold-only` 也属于 `arm_sdk` 路线，不是调试模式兼容入口。

对当前吊装逐电机验收，建议保持调试模式，准备并验证专用底层逐轴程序。不要为绕过 RPC 错误而在吊装中盲目进入锁定站立/运动，也不要仅删除 FSM 检查或将主题替换成 `rt/lowcmd`。专用程序需要明确其余关节的状态、受控轴的限幅和退出处理；现有程序的权重 0 释放方式不能直接用于底层电机命令。

用户截图的锁定站立→运动组合键为 `R2+X`，官方 Motion Wiki 的示例为 `R1+X`，说明这些资料的版本存在差异。此处只依据模式/接口关系判断，不据此提供未经本机固件核对的切换按键序列。官方底层示例还会使全身向零位移动并摆动踝关节，不能直接当作当前的小幅单轴验收程序运行。

## 为什么刚才没有完成单关节动作

机器人没有返回“禁止单电机控制”。两次右肘测试都在上身接管阶段被本地测试程序中止，尚未开始右肘 +5° 轨迹。第二次左肩 Pitch 的反馈速度达到 `0.74245 rad/s`（约 42.5°/秒），超过程序自定的 `0.6 rad/s` 保守停止线；该帧角度相对起始只变化约 0.387°。这些是接管时的反馈，不是右肘目标速度。电机错误码检查为 0。

目前没有定位这一短暂变化的原因，不能归因为电机损坏、固件不支持或某个电机被锁定。换成腕关节仍会经过同一接管过程，不能保证解决它；本工具保留停止条件，不自动重试或放宽阈值。

### 用户追加报错与脚本修正

用户随后提供了两次左腕 Pitch（20）的完整日志：

| 请求 | 中止时刻 | 触发关节 | 实测速度 | 相对起始变化 |
| --- | --- | --- | --- | --- |
| +2° | 0.14717 秒 | 左肩 Pitch（15） | 0.78386 rad/s，约 44.9°/秒 | 0.569° |
| −2° | 0.14498 秒 | 左肩 Pitch（15） | 1.05078 rad/s，约 60.2°/秒 | 0.702° |

两次均在 `engage` 阶段，距手腕轨迹开始的 5 秒尚早。该帧 `q == desired`，位移也未超过 0.15 rad，所以原先笼统的 `tracking/velocity stop` 实际均为速度保护。`[Reader] take sample error` 出现在中止/释放之后；机上 SDK 的通用异常捕获会打印这句话，未附异常原因。不能把它当作导致此次中止的电机报错，也不能仅凭该文字确定 SDK 异常根因。

代码复核确认原接管策略存在保持逻辑问题：一边每帧把参考更新为实测位置，一边把 `Kp/Kd` 同时从零渐增。按日志最后已发送帧的权重反算，两个命令的 `Kp` 分别为 0.07500/0.07290，`Kd` 为 0.002812/0.002734，远低于设定的 40/1.5。它不能实现此前所说的固定起始姿态保持。这是本脚本的问题，不是用户命令问题；它对实机瞬态的具体贡献仍需验证。更早的另一接管策略也曾中止，因此不能把此问题宣称为唯一根因。

本次修正为固定接管前参考，保持 `Kp=40、Kd=1.5`，仅对 SDK 接管权重渐变。官方 [G1 Python 示例](https://github.com/unitreerobotics/unitree_sdk2_python/blob/master/example/g1/high_level/g1_arm7_sdk_dds_example.py)同样保持非零增益；[官方运动模式说明](https://github.com/unitreerobotics/xr_teleoperate/wiki/Motion)解释了权重混合与切换风险。这里没有照搬官方示例的大幅归零/抬臂轨迹，也没有把接管权重直接跳到 1。原有速度、偏差、温度、力矩和遥测保护保留。

增加 `--hold-only` 可把接管问题与目标动作分开：零目标位移、5 秒权重渐增、1 秒保持、3 秒释放。新增报错会记录具体关节名、触发指标、限值和最后已发送命令参数。软件模拟验证固定参考/增益、默认不创建发布器、速度中止和释放流程；尚未通过修正后主动实机接管，不能宣称电机控制恢复。

**本次机上复查状态：**新脚本已同步并核对 SHA-256，旧版保存在同目录 `upper_body_check.3feeaaf.py`。运行不带 `--execute` 的预检，两次均在运控 RPC 查询处返回 `3102`；机上 SDK 定义其为 `RPC_ERR_CLIENT_SEND`。SSH、控制板 Ping 和独立 LowState 采样仍可用，但此次采样的 29 轴 `mode` 均为 0，已不同于之前脚本要求的 1。用户随后确认现场切入了调试模式；本程序没有自动启用电机、重启运控或更改模式。此状态下当前脚本仍应拒绝接管，不能跳过预检强行运行。

SSH 的作用是登录 Jetson 并运行 Python。Python 使用 DDS 发布命令：

`Mac → SSH → Jetson Python → rt/arm_sdk → 机器人上身控制`

在[宇树官方 arm_sdk 示例](https://github.com/unitreerobotics/unitree_sdk2_python/blob/master/example/g1/high_level/g1_arm7_sdk_dds_example.py)中，`motor_cmd[29].q` 是上身接管权重，12–28 是腰和双臂。可以只改变一个关节的目标角度，同时保持其他上身关节；这不等于独立接管一个电机。不要把其余关节目标置零，也不要把这个消息改发到全身 `rt/lowcmd`。完整底层控制需要协调全身控制权和支撑，本轮没有验证该路径。

## 手动运行

以下命令登录后在机器人上执行：

```sh
ssh unitree@192.168.123.164
cd /tmp/g1-acceptance-01a0bdf8

# 查看可选关节；这一步不连接 DDS
python3 upper_body_check.py --list-joints

# 检查 14 轴状态以及各自 +2° 目标是否在参考范围内，不发送运动命令
python3 upper_body_check.py --check-all

# 单独预检左腕 Roll 的 +2° 目标，不发送运动命令
python3 upper_body_check.py --joint left_wrist_roll --delta-deg 2
```

主动执行仍属于实验性测试，完整接管和运动尚未实机通过。执行时须维持本次已确认的吊装、清空双臂活动空间、受训操作员现场观察、遥控停止可用；现场不要同时操作姿态网页或运行其他 SDK 控制程序。预检 PASS 仅代表启动前条件满足，不能证明随后动作安全或电机验收通过。修正后的下一阶段应先验证零目标位移接管；当前不要重复旧版手腕命令或连续换轴试探。

```sh
# 不带 --execute 只预检
python3 upper_body_check.py --hold-only

# 会接管上身；目标保持启动姿态，9 秒后释放
# 零目标位移不保证实际不动，仍须现场监护
python3 upper_body_check.py --hold-only --execute
```

只有接管、保持和释放的反馈及现场观察都确认稳定后，才进入以下逐关节测试阶段：

```sh
# 会发送运动命令：左腕 Roll +2°，然后返回接管前的固定参考角度
python3 upper_body_check.py --joint left_wrist_roll --delta-deg 2 --execute
```

一次运行完成后人工核实停止、异响和回位，再选择下一轴。负方向用 `--delta-deg -2`。参数是角度，代码内部转换为弧度；正负号对应关节坐标轴，不统一等于“抬起/放下”。这是一次自动回位测试，不是连续遥控器或保持任意姿态的命令行。

如果再次出现 `abort`，保留输出并停止追加动作，结合厂家/卖家对当前控制模式和接管行为的说明处理。`Ctrl+C` 会请求脚本退出并发送权重 0；网络断开、进程崩溃或强制终止时不能靠脚本保证释放，现场遥控停止仍须在手边。

## 可以选择哪些关节

命令中的名称是 `left_` 或 `right_` 加上下表后缀，例如 `right_shoulder_pitch`。

| 部位 | 名称后缀 | 左侧索引 | 右侧索引 |
| --- | --- | --- | --- |
| 肩俯仰 | `shoulder_pitch` | 15 | 22 |
| 肩侧摆 | `shoulder_roll` | 16 | 23 |
| 肩旋转 | `shoulder_yaw` | 17 | 24 |
| 肘 | `elbow` | 18 | 25 |
| 腕旋转 | `wrist_roll` | 19 | 26 |
| 腕俯仰 | `wrist_pitch` | 20 | 27 |
| 腕偏转 | `wrist_yaw` | 21 | 28 |

这 14 轴入口不包括腰部或灵巧手手指。腰部三个关节仍随上身接管并参与姿态保持。

轨迹时序为：5 秒渐进接管、3 秒到目标、1 秒保持、3 秒返回、1 秒保持、3 秒释放。默认 2° 的目标轨迹最大速度约 1°/秒；允许的最大 5° 偏移对应最大目标速度 2.5°/秒。接管时其他关节的实际运动仍以反馈保护为准。

角度范围来自[官方 G1 29 轴 URDF](https://github.com/unitreerobotics/unitree_ros/blob/master/robots/g1_description/g1_29dof.urdf)，起点和终点均留 5° 余量。这只是参考关节边界，未做碰撞检测，不能替代现场空间检查或实际配置核对。

## 保护和结果如何理解

程序绑定本次观测的 `FSM 802 / mode_machine 5 / mode_pr 0 / eth0`；现有姿态服务 `http://127.0.0.1:8080/status` 必须为 `IDLE`。不满足会退出，不会自行切换模式或关闭原服务。

遥测 CRC、100 ms 新鲜度、29 轴错误码/模式、60°C 温度、遥控按键以及运动中的跟随偏差、速度、估算力矩和下肢位移均设有中止检查。这些是本次测试的保守限制，不是厂家额定值或认证安全功能。状态检查不能保证总线上不存在别的控制器。

- `all_joint_preflight` / `preflight`：只读预检；没有证明驱动能力。
- `abort`：中止原因，退出码 1；不要登记为动作通过。
- `release_sent`：程序发送了权重 0，未收到机器人完成释放的确认。
- `completed`：程序走完整个时间序列，仍需检查实际轨迹及现场观察，不能单凭这个字段判断采购验收通过。

官方 `G1ArmActionClient.GetActionList()` 本轮也已读通，机上列出抬手、握手等预设动作。它们是协调动作接口，不适合作为单电机定位证据，本轮未调用执行。

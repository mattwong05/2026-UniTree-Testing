## 报错原因与适配

1. **USB 重枚举期间序列号文件短暂消失。** 初次现场快照相机仍位于 USB 2 总线，随后在 USB 3 总线重新出现并稳定返回序列号。原程序将这一状态直接输出为缺少 `/sys/.../serial` 文件。现在最多重试 3 次，总探测预算 5 秒，并给出检查供电、USB 3 数据线和重新连接的提示；仍保留 D435i 身份、唯一 Z16 节点与探测前后身份一致性检查。
2. **SDK 只在登录目录可导入。** 02 的 SDK 位于 `/home/unitree/unitree_sdk2py`。旧启动器用 `python3 -c` 预检可以导入，但执行 `/tmp/.../sensor_server.py` 后搜索路径改变，RGB 和 LiDAR 报 `No module named unitree_sdk2py`。启动器现验证实际子模块，并为服务固定解释器与 SDK 父目录，无需安装或移动依赖。
3. **头部视频服务原本停止。** `video_hub_pc4` 初始状态为 1，胸部服务为 0，原彩色 RPC 超时。新流程在核对官方服务配置和 D435i RGB 接口后临时开启头部服务；停止时恢复并确认。胸部、运动和 SLAM 服务未被本工具切换。

网页现显示 USB 速度、总线路径和通过当前查询确认的雷达型号。无法确认型号时保留未知状态，不依据设备日期推断；MID360s 字符串可识别，但未完成 MID360s 实机点云验证。

## 验证证据

- 浏览器实际显示彩色画面、深度伪彩图和三维点云。三路接收约 9–10 Hz；雷达单帧约 20064 原始点，预览抽样为 6000 点。
- 重复连接后连续取 12 次样本，三路均为 live，彩色、深度各得到 12 个不同的 JPEG，点云得到 12 个不同序列号，均为 6000 个预览点。帧不是冻结的旧数据。
- 停止后 `video_hub_pc4` 和 `lidar_driver` 的初始状态、恢复状态均为 1，`restore_confirmed=true`，无清理错误。停止后的彩色快照、深度快照和点云接口均返回 HTTP 409。
- 首轮停止后启动器 `Ctrl+C` 退出码为 0；更新后再次启动、连接并获取三路数据成功。
- Mac 本地 157 项测试，156 通过，1 项因无 OpenCV 跳过。机器人现有 Python 3.8/OpenCV 环境执行 70 项后台、LiDAR 和视频服务模拟测试，全部通过，包含颜色测试；模拟测试不访问真实设备。另通过 Python 3.8 语法、浏览器脚本语法与 `git diff --check`。

原始数据保存在忽略 Git 的 `evidence/2026-09-20/sensor-web-02/`，包括 `live-status.json`、`repeat-live-samples.json`、`stop-status.json`、彩色/深度快照、预览点云以及本地/机载测试日志。

## 复现

结束上一台的启动器并换接目标机器人后，在本项目目录运行：

```sh
python3 scripts/start_sensor_web.py --host 192.168.123.164 --name g1-02
```

输入 SSH 密码后打开打印的本地地址，点击「连接预览」，核对相机和雷达序列号。端口占用时使用 `--port 8766 --remote-port 8766`。完整停止、租约与换机说明见 [传感器网页使用说明](../docs/sensor-web.md)。项目无既有版本或更新日志体系，此次未新增版本号。

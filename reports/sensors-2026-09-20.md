# G1 LiDAR 与摄像头网络实测

日期：2026-09-20，Asia/Shanghai。采集窗口约 17:55–18:10。本次是既有设备的传感器功能短测，不是整机或测距精度验收。

## 结果

**可以继续通过网络得到检查结果。** Mac 经现有网线连接机载 `.164` 计算单元，在机器人上读传感器并通过 SSH 取回统计、原图和点云。用户现场插接头部 USB-Type-C 后，机载电脑才枚举出 D435i；该 USB 连接与 Mac 的网络读取链路是两个环节。

| 项目 | 实测 | 结论 |
| --- | --- | --- |
| RGB 彩色图像 | 20.15 秒，200 张成功解码且内容不同的 1920×1080 图像；读取失败 0 | 本次彩色成像/取图功能正常 |
| 原始深度 | 10.00 秒，892 帧 640×480 Z16；892 个不同序号 | 本次深度流功能正常；未验证距离标定 |
| MID360 点云 | 20.00 秒，200 帧，约 9.97 Hz；200 个不同载荷且时间戳递增 | 雷达采样和机器人点云发布可用 |
| MID360 状态 | SAMPLING；两次读取温度 64.10/64.35°C；HMS `0x01040002` | 有光学窗口脏污警告，不能登记为无异常通过 |

HMS `0x01040002` 的异常编号是 `0x0104`，级别 `0x02` 为警告；厂家的解释为窗口脏污可能影响点云可靠性，建议清洁窗口。需要现场检查灰尘、保护膜和遮挡，并按厂家清洁方式处理后复测。报警不等于已证明雷达损坏，也不能因能输出点云就忽略。[Livox 官方 HMS 表](https://livox-wiki-en.readthedocs.io/en/latest/tutorials/new_product/mid360/hms_code_mid360.html#diagnostic-codes-table)

## 摄像头证据

开头 `.164` 未枚举相机，`/dev/video*` 不存在。18:01:44 起，内核记录 Intel RealSense Depth Camera 435i（USB `8086:0b3a`，序列号 `253843060484`）连接、断开和切换端口；用户明确确认正在现场插拔调整，不能把这些事件归为非预期掉线。18:02:04 后相机位于 USB `2-2.2`，出现 `/dev/video0`–`/dev/video5`。

既有 `videohub_pc4` 使用 `/dev/video4`。直接打开 RGB 节点返回 EBUSY，说明被现有服务占用，不作为硬件故障。改用该服务已有的 `GetImageSample` 接口后立即返回 1920×1080 图像。约 10 次/秒轮询 20 秒，共 200 张不同的解码图像，最大接收间隔 0.142 秒；这个速率是本程序取图速率，不是相机原生帧率。人工查看原图能识别现场机器人、支架、地面和人员活动。

机上未安装 `pyrealsense2`，现有 OpenCV 对该节点 Z16 格式初始化不成功，因此使用仅依赖 Linux V4L2 的小型 C 工具直接读取 `/dev/video0`。工具未改曝光、激光器、深度标定、帧率或厂家服务，只设置本节点临时采集格式、取帧、释放缓冲，并核实恢复原格式。

- 10 秒收到 892 个完整帧，观测速率约 89.20 帧/秒（包含启动时间）。
- 序号 0–891，无重复、跳号、回退；时间戳无重复、回退或非法值。
- 错误标志帧、短帧、全零帧均为 0；全部帧平均非零像素比例 74.00%。
- 最后一帧零值比例 26.10%，数值 65535 比例约 0.0023%；非零像素不能直接视作经过准确度验证的有效距离。
- 保存的是原始 Z16 值，没有读取深度比例参数，报告和预览均不将其直接标为毫米。预览按非零且非 65535 值的 2%–98% 分位缩放，黑色代表这些排除值。
- 工具明确记录 `streamoff=ok`、`format_restore=ok`，退出码 0。

## LiDAR 证据

依据用户提供的[宇树官方 LiDAR 接口](https://support.unitree.com/home/zh/G1_developer/lidar_services_interface)，本机订阅 `rt/utlidar/cloud_livox_mid360`，类型 PointCloud2，官方预期 10 Hz、坐标帧 `livox_frame`。没有使用导航或建图指令。

只读 Livox 广播发现和参数查询确认：MID360，序列号 `47MCN8R0037833`，IP `192.168.123.120`，MAC `8c:58:23:bd:d3:cc`，应用版本字节 `13.18.2.40`。首次单播发现无回复；[官方协议](https://livox-wiki-en.readthedocs.io/en/latest/tutorials/new_product/mid360/livox_eth_protocol_mid360.html)规定发现使用广播，按该方式重测成功，不把首次超时算作硬件异常。响应校验来源、命令、序号、CRC16、CRC32和参数长度。

原始 UDP 点云和 IMU 的目的地分别为 `.161:56301`、`.161:56401`。所以只在 `.164` 查 USB 或被动监听其他端口不能判断雷达是否工作。DDS 域 0 的首次发现没有点云发布端；官方话题的 3 秒直接订阅也为零帧。服务列表同时显示 `lidar_driver=1`，即已关闭；[官方设备状态接口](https://support.unitree.com/home/zh/G1_developer/robot_state_client_interface)的状态值为 0 已开启、1 已关闭，开关参数则为 1 开启、0 关闭。

临时开启原有 `lidar_driver` 后，服务状态变为 0，`ai_sport` 与 `unitree_slam` 均保持 1（关闭），其他服务列表也不变。20 秒订阅结果：

- 200 帧，接收频率 9.9697 Hz，最长接收间隔 0.1143 秒。
- 帧坐标名均为 `livox_frame`，时间戳没有重复或倒退，200 个点云载荷各不相同。
- 共 4,011,072 点；全部 XYZ 为有限数，其中 1,846,768 点距离非零，占 46.04%。零点没有被当作有效障碍物。
- 每帧 19,392–20,623 点，第一帧 `point_step=22`，实际字段含 XYZ、intensity、ring 和 time；按字段偏移、行步长和字节序解析，解码错误 0。
- 非零坐标距离范围约 0.0986–7.5459（设备坐标单位）；没有使用已知标尺做精度校验。首帧投影可见现场几何轮廓，但不据此签署平面精度或标定验收。

本地证据：[首帧 XYZ 数组](../evidence/2026-09-20/sensors/lidar-first.npy)、[首帧三向投影](../evidence/2026-09-20/sensors/lidar-preview.png)。HMS 警告在测试前后都存在。诊断汇总字段为 0 不能覆盖独立的 HMS 警告。

## 退出状态与变化

雷达测试结束发送关闭请求。请求返回成功后一秒服务列表仍暂时为 0，不能据此宣称已恢复；后续独立查询已确认 `lidar_driver=1`，完整服务列表与测试前一致。未发送关节、行走、SLAM导航、运动模式或复位命令。

点云和 IMU 的目的 IP、目的端口保持原值；两项配置中的**源端口字段从 0 变为 56300/56400**，与[厂家 SDK 驱动初始化](https://github.com/Livox-SDK/Livox-SDK2/blob/master/sdk_core/command_handler/build_request.cpp)行为一致。服务启停状态已恢复，但参数没有逐字节恢复。没有为恢复数字 0 再写入雷达配置，也不推断参数 0 表示测试前实际 UDP 源端口为 0。

没有安装依赖、升级固件或新增常驻服务。深度工具仅在机器人 `/tmp/g1-sensors-01a0be3c/` 编译运行。最后追加的 RGB 复查因共享 SSH 认证会话已结束而未执行；Mac 对 `.164` 的即时 Ping 仍成功。此前 200 张 RGB 及 892 帧深度证据已经完整保存。

## 工具与复现

沿用现有机上 Python 3.8、Unitree SDK、Cyclone DDS、NumPy、OpenCV 和 GCC，不修改 Python 环境。SSH 密码按交互提示输入，不写入代码或文档。

```sh
# 读取现有厂家视频服务，原图留在指定的机上临时目录
ssh unitree@192.168.123.164 \
  'timeout --kill-after=2 28 python3 - --seconds 20 --output-dir /tmp/g1-sensors-review' \
  < scripts/camera_sample_check.py > camera-rgb.jsonl

# MID360 广播发现与参数查询，仅查询单个目标，不改模式或输出地址
ssh unitree@192.168.123.164 \
  'timeout --kill-after=2 12 python3 - --host-ip 192.168.123.164 --lidar-ip 192.168.123.120 --broadcast-discovery --timeout 3' \
  < scripts/livox_readonly_probe.py > lidar-status.jsonl

# 仅订阅；lidar_driver 关闭时零帧是预期结果，脚本不会自动开服务
ssh unitree@192.168.123.164 \
  'timeout --kill-after=2 27 python3 - --seconds 20 --output-dir /tmp/g1-sensors-review' \
  < scripts/lidar_cloud_check.py > lidar-cloud.jsonl
```

需要复测点云时，先记录服务状态，按官方接口仅开启 `lidar_driver`；结束后关闭并轮询确认恢复。官方[导航文档](https://support.unitree.com/home/zh/G1_developer/slam_navigation_services_interface)分别列出雷达驱动与导航服务，不能为取原始点云连带启用导航。

深度工具在机上编译与运行（先确认 `/dev/video0` 仍是本相机未被占用的深度节点；输出文件必须不存在）：

```sh
ssh unitree@192.168.123.164 'mkdir -p /tmp/g1-sensors-review'
ssh unitree@192.168.123.164 \
  'gcc -x c - -std=c11 -O2 -Wall -Wextra -Wpedantic -o /tmp/g1-sensors-review/depth_frame_check' \
  < scripts/depth_frame_check.c
ssh unitree@192.168.123.164 \
  'timeout --kill-after=3 20 /tmp/g1-sensors-review/depth_frame_check --device /dev/video0 --seconds 10 --output /tmp/g1-sensors-review/depth-last.pgm'
```
